# ADR-057 P10 收尾修正：第二後端、查詢規模、量測、備份排程與 SBOM

**Status: ACCEPTED**（owner 架構審批，2026-10-25）

**Spec references:** §6.2、§6.3、§6.4、§17.1（DB-01、DB-002、DB-008、DB-010、OPS-001、REP-003、SR-004）、
§28.3、§29.4（FM-010）、§31.4（bounded work）、§38.3（R4、R8）
**Related:** ADR-021（無 vendor SDK）、ADR-022（不得靜默降級）、ADR-048（三 profile）、ADR-055／ADR-056

## 1. Context

ADR-056 留下五個未達標項目。本 ADR 記錄把它們推到「可執行證據」等級的決策與結果，
並明列哪一項**仍然不能**在不違反專案約束的前提下完成。

| # | ADR-056 的缺口 | 本 ADR 的結果 |
|---|---|---|
| 1 | Profile B/C 未實作，三方等價不成立、DB-01 blocked | **Profile B 已實作為真正的 SQL 後端**並通過同一契約；profile C 仍需三台伺服器（不能在此環境完成） |
| 2 | 1M episode 未達標（`MAX_CANDIDATES` + O(n) 檢索） | **已達標**：候選索引把上限套用在「匹配數」，1M episodes 實測 0 失敗 |
| 3 | RSS／on-disk 未量測 | **已量測**（Windows `K32GetProcessMemoryInfo`；SQL checkpoint 後檔案大小）；VRAM 為 not applicable |
| 4 | 無 backup 排程／SBOM | **已補**：`BackupScheduler`（interval/retention/rollback 演練）＋ CycloneDX 1.5 SBOM ＋ SHA-256 digest gate |
| 5 | JSON Schema 仍 preliminary | **未變更**：schema closure 屬 wire 契約批准範圍，需 owner 決策（見 §6） |

## 2. Decisions

| ID | 決策 | 理由與後果 |
|---|---|---|
| **D-01** | 新增**真正的 SQL 後端** `ukma-adapter-sqlite`：metadata／manifest／writer fence／outbox 全部在 SQL 交易內（`BEGIN IMMEDIATE`…`COMMIT`，`journal_mode=WAL`、`synchronous=FULL`），full-text／vector 仍為 derived projection | profile B 需要「不是 JSON 檔」的後端。`rusqlite` **bundled** 在本地編譯 SQLite 原始碼，因此不需要伺服器，契約測試可完整執行。ADR-021 只禁止 domain 依賴 backend SDK；adapter 內部使用自己的 SDK 是原本設計 |
| **D-02** | `arc001` 的禁用清單改為**範圍限定**：backend SDK 只允許出現在 `crates/adapters/` 之下，其他 crate 一律禁止；`db001` 對 16 個 domain crate 仍然完全禁止 | 這比原本「全域禁止」更精確也更嚴格地保護 domain 中立性。若日後有人把 `rusqlite` 加進 domain crate，兩個 gate 都會失敗 |
| **D-03** | Profile 報告改為 A、B **available**、C unavailable；並新增 `two_way_equivalence` 區塊（同一份契約＋相同寫入產生相同 revision/etag/key order） | 「三方等價」在沒有 PostgreSQL/Qdrant/Neo4j 的環境下不可能誠實宣稱；報告明確寫出「verified: A/B」與「not_verified: three-way」 |
| **D-04** | 搜尋候選改由 `search::CandidateIndex`（倒排 postings，`u32` slot）挑選，且 `MAX_CANDIDATES` 改為套用在**匹配數**；≤ 10 000 筆仍走原本的直接掃描路徑 | 小語料語意與測試完全不變；大語料從「> 10 000 直接 RESOURCE_LIMIT」變成可查詢。1M 實測 search P50 204 ms、0 失敗 |
| **D-05** | 索引新鮮度用**語料指紋**（`(id, tombstoned, head etag)` 的 FNV-1a）判定，而不是逐一 hook 每個 mutation | head etag 由內容導出，任何 revision／tombstone／新增都會改變指紋，因此不可能漏掉 invalidation。代價是每次查詢 O(n) hashing（1M 約 100 ms），已在基準文件記錄為已知可優化點 |
| **D-06** | 「匹配全部」的查詢仍然回 `RESOURCE_LIMIT` | 有界工作量是 §31.4 的硬要求；寧可回錯也不靜默截斷或全表掃描。`scale_contract.rs` 固化此行為 |
| **D-07** | 量測改為**實測**：process RSS 走 OS API、SQL on-disk 走 checkpoint 後檔案大小；VRAM 明列為 not applicable（不用 GPU） | 「未量測」與「不適用」是不同狀態，報告分開表達 |
| **D-08** | `storage-router::backup` 提供 `BackupPlan`／`BackupScheduler`（`tick(now)` 回傳 `Backup`/`Idle`、retention、prune、時鐘倒退保護、`report_json`），備份與還原本身由 host 執行 | 沒有背景執行緒就沒有隱藏狀態：錯過的 tick 在 history 中是可見的缺口。`disaster_recovery.rs` 用排程器做「三次 tick → 保留 2 份 → 從最新備份還原」 |
| **D-09** | SBOM 為 CycloneDX 1.5 JSON（331 components，`pkg:cargo/...` purl、每個 component 帶 licence）；另存 `sbom.digest.json` 記錄 SHA-256、位元組數與 `signature: null` | R8 要可審核的清單。**digest 不是簽章**：檔案內明文寫出這點，避免把完整性檢查說成簽章 |
| **D-10** | SBOM 與 inventory 都由 `cargo metadata --locked` 產生，並由 `release_evidence.rs` 驗證（與 `Cargo.lock` 雙向對齊、digest 重算、licence 逐項重推導） | 新增依賴未更新 → build 失敗；這正是 gate 的價值（本次 `rusqlite` 加入時就擋了一次） |

## 3. 驗證結果

| 驗證 | 結果 |
|---|---|
| SQL 後端契約 | `ukma-adapter-sqlite` 8 unit tests＋`port_parity` profile B 全綠 |
| 兩後端等價 | `the_two_available_profiles_agree_on_what_they_store`：5 次相同寫入產生相同 revision/etag/順序 |
| 大語料查詢 | `scale_contract` 2 tests：> 10 000 筆可查、改寫後重新索引、超量匹配被拒 |
| 1M 基準 | [scale-probe-1m.json](../../docs/performance/scale-probe-1m.json)：store P50 0.011 ms、search P50 204 ms、**失敗率 0**、RSS 3 721 MiB、SQL on-disk 207 MiB |
| 排程備份 | `a_scheduled_backup_restores_and_old_backups_are_pruned` |
| SBOM／授權 | `the_sbom_covers_every_locked_package`、`the_sbom_digest_matches_the_file`、授權 gate 6 tests |

**覆蓋矩陣**：69 項全部有處置 → `covered` **63**、`partial` **5**、`gap` **1**（僅 FM-006 仍是 gap）。
`FM-010`、`SR-004` 由 partial/gap 轉為 covered；`DB-01` gate 由 blocked 轉為 passed
（兩個 production-capable 後端通過同一契約）。

## 4. 仍未完成（不得宣稱完成）

1. **Profile C（hybrid）**：PostgreSQL + Qdrant + Neo4j 三台伺服器在此環境不存在；adapter 仍宣告 unavailable。
   三方等價**未驗證**。
2. **FM-006（canonical schema migration）**：仍無 migration runner／版本升級路徑，維持 `gap`。
3. **SBOM 未簽章**：只有 SHA-256 digest，沒有金鑰與簽章流程。
4. **JSON Schema 仍 preliminary**：見 §6。
5. **1M 查詢延遲的指紋成本**：每次查詢 O(n) hashing，1M 約 100 ms；增量維護指紋可再降一個數量級。

## 5. 未變更的東西

- `operation-registry.yaml`／`error-registry.yaml`：未新增或刪除任何 operation 或 error code。
- §31.4／§31.5 envelope 與 error envelope 語意未變更；`MAX_CANDIDATES` 的**數值**未變，只改變它量測的對象
  （全部可見文件 → 匹配文件），並由 `scale_contract.rs` 固化新語意。
- 小語料（≤ 10 000 筆）的檢索路徑與 BM25 統計完全未變，因此既有 MAPI 測試不受影響。

## 6. 需要 owner 決策：JSON Schema closure

`contracts/schema/v1` 仍有多處 `$comment: "UNRESOLVED TYPE: …"`（例如
`traceability.propose_link.request.schema.json` 的 `input.link`），且 trace 的 wire enum 是
`UPPER_SNAKE` 而 §34.1 對 memory 要求 lowercase。把 schema 從 preliminary 升為 closed 等於
**改動 wire 級公開語意**，依 `.github/copilot-instructions.md` 必須先取得明確架構批准，因此本階段不動。

建議的批核項目（拿到批准即可執行）：

1. 以 Rust 型別為 IDL，把 `UNRESOLVED TYPE` 全部展開成具體 `$defs`（69×2 schemas 重生成）。
2. 統一 enum 大小寫策略：trace 改 lowercase（破壞性）或 §34.1 註記為 memory-only（非破壞性）。
3. 為每個 operation 補 `required` 與 bounds，並把 414 fixtures 提升為 positive/negative 對照閉環。
4. 之後才把 `claim_level.schema_closed` 由「檔案存在」改為「schema 閉合」的正式宣告。
