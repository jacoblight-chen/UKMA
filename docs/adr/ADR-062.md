# ADR-062 — Close the last four caveats: three-way parity, in-database full-text/vectors, signed SBOM, derived claims

- Status: accepted
- Date: 2026-10-25
- Closes the four items ADR-061 listed as "not claimed"
- Related: ADR-038 (fail closed), ADR-057 (SQLite), ADR-059 (migration + signing), ADR-061 (profile C adapters)

## 1. Three-way parity in one assertion

`crates/ukma-integration/tests/three_way_parity.rs::the_four_profile_c_ports_agree_in_one_run`
drives **all four profile-C ports in a single test run**:

- the same write set (4 records, one stale CAS, a paged read, two manifest writes, three
  outbox events, one ack) goes through embedded, SQLite and PostgreSQL, and the
  observations — revisions, content etags, page contents, cursor, manifest value, pending
  order after the ack — must be **identical** across the three;
- Qdrant must answer the same neighbour order (`a, c, b`) as the reference cosine ordering,
  and honour a metadata filter;
- Neo4j must store the same nodes/edges, answer the same incoming/outgoing ids and cascade
  the delete of a node into its edges.

Without `UKMA_POSTGRES_DSN` / `UKMA_QDRANT_URL` / `UKMA_NEO4J_URL` the test reports a skip:
no services must not fail the build, and must not claim parity either.
`contracts/testing/port-parity.json` now records `three_way_equivalence.verified = true`
with the test path and the required variables.

## 2. PostgreSQL full-text and vectors run in the database

The adapter no longer delegates the derived ports:

- **full-text** — `fulltext(scope, analyzer, id, revision, fields JSONB, all_text)` with
  `to_tsvector('simple', …)` / `plainto_tsquery` and `ts_rank_cd` ranking, ordered
  `(score desc, id asc)`; `field` scoping uses `fields ->> $field`; `analyzers()` reports the
  analyzers the store actually holds. The `analyzer` argument is the isolation label, the
  tokenisation is PostgreSQL's `simple` configuration — stated, not hidden.
- **vectors** — `vector_profile` keeps the profile (dimension, metric, model identity)
  durably, so `profile()` survives a reconnect; `vector_item` stores `REAL[]` plus a JSONB
  metadata map, and search is **exact k-NN inside the database** (`unnest` join for cosine /
  dot / squared L2, `ORDER BY score DESC, id ASC`), optionally filtered with
  `metadata @> $filter::jsonb`. No in-process copy, no ANN approximation.
- `postgres` gained the `with-serde_json-1` feature so JSONB parameters are bound natively
  instead of being stringly typed.

Evidence: `cargo test -p ukma-adapter-postgres` → **11 passed**, including
`fulltext_is_ranked_inside_the_database` and
`vectors_are_searched_in_the_database_and_the_profile_survives_a_reconnect`.

## 3. The SBOM is signed

`ukma-release-evidence -- generate-key --out <path outside the repo>` produced an Ed25519
key at `%USERPROFILE%\.ukma\release.key`; `-- sign` wrote `contracts/testing/sbom.signature.json`
and **recorded the provenance in `sbom.digest.json`** (`signature`, `signature_algorithm`,
`public_key`). `-- verify` recomputes the digest and checks the signature.

The private key never enters the repository. The gate
`the_sbom_digest_matches_the_file` accepts either state but never a lie: signed ⇒ the manifest
must name the signature file, the algorithm must be `ed25519`, the signature must cover the
current SHA-256 and both files must name the same public key; unsigned ⇒ `signature: null` and
the "not a cryptographic signature" note.

## 4. The claim level is derived, not asserted

`crates/ukma-integration/tests/claim_level.rs` recomputes the four flags and requires
`docs/implementation-status.yaml` to agree:

| flag | derivation | value |
|---|---|---|
| `catalog_defined` | 69 registered operations | **true** |
| `schema_closed` | the contract gate (SCHEMA-01/02/03, no placeholders) | **true** |
| `implementation_compliant` | `gap == 0 && partial == 0` over all 69 classified ids | **false** |
| `production_ready` | the above **and** verified profile C **and** signed SBOM **and** a licence-clean inventory | **false** |

A hand-set flag is a promise; this makes it a measurement, and a false claim must name its
blockers: the test prints the five ids that are still `partial` (DB-005, MEM-006, FO-005,
ML-002, SR-001) instead of leaving "why not" implicit. `production_ready` stays false for the
same reason — it inherits `implementation_compliant`.

## 6. Still not claimed

- `implementation_compliant` / `production_ready` are **false by derivation**: five §17.1 ids
  remain `partial`, and closing them is domain work (cross-domain TTL, zh/en/ja synonym
  queries, …), not plumbing.
- The services are local user processes started by `tools/profile-c/start.ps1`; that is a
  reproducible development topology, not a deployment (no TLS, no auth beyond a dev password,
  no HA).
