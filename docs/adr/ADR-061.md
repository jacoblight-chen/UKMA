# ADR-061 — Profile C adapters are real, and configuration driven

- Status: accepted
- Date: 2026-10-25
- Closes: the "profile C unavailable" limitation recorded in ADR-056 … ADR-060
- Related: ADR-021/022 (no backend SDK outside adapters), ADR-038 (fail closed), ADR-057 (SQLite), ADR-059 (migration)

## 1. Context

Profile C (PostgreSQL + Qdrant + Neo4j) was declared unavailable because the three
adapters were ~1 KB skeletons. The owner approved installing the services locally
and implementing them.

## 2. What was actually installed (user scope, no admin)

| Service | Artifact | Endpoint |
|---|---|---|
| PostgreSQL 16.4 | portable binaries zip, `initdb -A trust` | `127.0.0.1:55432` |
| Qdrant 1.20.0 | `qdrant-x86_64-pc-windows-msvc.zip` | `127.0.0.1:6333` |
| Neo4j 5.26.0 | community zip + Adoptium JDK 21 | `127.0.0.1:7474` |

None of them is registered as a Windows service; they run as user processes under
`F:\ukma-services`, outside the repository.

## 3. Decision

1. **PostgreSQL** (`crates/adapters/postgres`, `postgres` 0.19) serves
   `MetadataPort` (CAS with `SELECT … FOR UPDATE`, manifests, single-writer
   fencing), `OutboxPort` (durable, `(event_id, consumer)` dedup, dead letters),
   `SchemaVersionPort`/`MigrationStore` (FM-006) and delegates the derived
   full-text/vector ports to the in-process implementations — the same limit the
   SQLite adapter states. The DDL is serialised with a PostgreSQL advisory lock
   because `CREATE TABLE IF NOT EXISTS` is not atomic against a concurrent creator.
2. **Qdrant** (`crates/adapters/qdrant`, `ureq`) serves `VectorPort` over REST with
   **one collection per (scope, profile)**, so isolation is structural. Point ids
   are derived deterministically from the logical id and the logical id plus
   revision travel in the payload. The profile registry is process-local (Qdrant
   stores only dimension and distance), so `profile()` returns `None` after a
   restart instead of inventing an identity.
3. **Neo4j** (`crates/adapters/neo4j`, `ureq`) serves `GraphStore` over the HTTP
   transactional API with `(scope, id)`-keyed `:UkmaNode`/`:UkmaEdge` records,
   cascading node delete, deterministic id ordering and scope isolation.
4. **Synchronous clients only**: REST/HTTP instead of gRPC/Bolt, so no async
   runtime enters the workspace for these ports.
5. **Availability is configuration driven**: `capabilities_with(None)` reports
   unavailable with the variable that would enable it; `capabilities()` reads
   `UKMA_POSTGRES_DSN` / `UKMA_QDRANT_URL` / `UKMA_NEO4J_URL`. A machine without the
   services therefore still fails closed, and the committed `port-parity.json`
   describes exactly that state.
6. **A real bug was found by the new contract test**: both SQL adapters applied the
   `list` prefix only on the first page, so a cursor page could return keys beyond
   the prefix (`other:1` after `canon:*`). `prefix_upper()` now bounds every page in
   PostgreSQL **and** SQLite, with a regression test on both.

## 4. Evidence (executed 2026-10-25 against the live services)

- `cargo test -p ukma-adapter-postgres` → **9 passed** (CAS/etag, paging, fencing,
  outbox dedup, scope isolation, canonical migration, embedded equivalence,
  capability probe)
- `cargo test -p ukma-adapter-qdrant` → **6 passed** (profile round trip, dimension
  mismatch, upsert/search/filter/delete, scope isolation, capabilities)
- `cargo test -p ukma-adapter-neo4j` → **4 passed** (CRUD, cascade, scope isolation,
  capabilities)
- `cargo test -p ukma-adapter-sqlite` → **8 passed** after the prefix fix
- Every suite skips cleanly when its environment variable is absent, so CI without
  services stays green — and the parity report records which profiles were really
  exercised.

## 5. What this does not claim

- Three-way **equivalence** is now *possible* and partially proven (PostgreSQL is
  compared against the embedded adapter field by field, including etags). A full
  three-way assertion across all four ports at once is not yet written, and the
  services are local user processes, not a production deployment.
- PostgreSQL full-text/vector stay in-process; pgvector and `tsvector` are the
  documented next step, not a current capability.
- `claim_level.implementation_compliant` and `production_ready` remain **false**.
