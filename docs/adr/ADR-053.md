# ADR-053 Traceability 實作決策（P7）

**Status: ACCEPTED**（owner 架構審批，2026-10-25）

**Spec references:** §35.1、§35.2、§40.3、§29.4（TAPI-01..13、TRACE-001、PROP-06）
**Related:** ADR-049（P3 服務形狀）、ADR-050（P4）、ADR-051（P5）、ADR-052（P6）

## 1. Context

P7 交付 §35 的 13 個 traceability operation，以及 §40.3 的三維有效性模型。
**沒有新增或修改任何 wire 級 operation**，65-operation registry 與 §31.4 全域語意未變。

`crates/traceability-engine` 由 skeleton 變為可編譯、可測試的垂直切片：型別、狀態機、
三維有效性、coverage／impact／gap／evidence 分析，以及 §37 port。

## 2. Decisions

| ID | 決策 | 理由與後果 |
|---|---|---|
| **D-01** | `TraceState` **只是流程狀態**：`historical_validity`、`current_applicability`、`index_freshness` 三個維度獨立存放；來源改版只讓 `current_applicability=requires_revalidation`，歷史 `valid` 不變 | §40.3；TRACE-001／PROP-06。測試 `historical_validity_is_not_changed_by_a_new_head` 固化 |
| **D-02** | 撤銷（revoke）**不改寫歷史**：已驗證過的連結被 revoke 後 `historical_validity` 仍為 `valid`，但 `current_applicability=not_applicable` | §40.3「不得自動使歷史 valid 變 invalid」；由整合測試抓到的真實缺陷（原本回 `unverified`） |
| **D-03** | 狀態機完整實作 §35.2：`proposed→validated→accepted`、`proposed/validated→rejected`、`validated/accepted→stale`、`stale→validated`、`proposed/validated/accepted/stale→revoked`；`rejected`/`revoked` **terminal** | 不合法的轉移一律 `LINK_STATE_CONFLICT`，測試以矩陣覆蓋 11 條允許與 8 條拒絕 |
| **D-04** | accepted 後 **evidence immutable**：`append_evidence` 在 accepted 狀態回 `LINK_STATE_CONFLICT`，補證據需新 revision 並重審 | §35.2 明文；重複 evidence id 不重複儲存 |
| **D-05** | 有效性在查詢時**即時評估**：`observe_endpoint`（seam）記錄 head 變動，並把斷言舊 revision 的連結轉為 `stale`、重算 `ValidityVector`；index freshness 由 endpoint 記錄供給 | 不偽造 head；stale 與 index lag 是不同維度（§40.3 明文禁止以 `stale` 同時表示兩者） |
| **D-06** | Coverage：denominator = **已授權 in-scope requirements**；`unknown` **不計入 covered**；`denominator=0 → coverage_ratio=None`（不得輸出 100%）；任何 excluded 或 unknown → `coverage_incomplete=true` | §35.1；只有 `current_applicability=applicable` 且索引可用且狀態為 validated/accepted 的連結才算 covered |
| **D-07** | 非 `accepted_only` 時，`stale` 連結視為「**曾經**實作」→ 計入 qualifying 但落在 `unknown`；`accepted_only` 時則不計 | 讓「需要重驗」與「從未實作」在報表上可區分，避免把 stale 誤報成 uncovered |
| **D-08** | Impact 為有界 BFS：`max_depth ∈ 1..=10`、候選上限 5000 → `RESOURCE_LIMIT`；遇到 `requires_revalidation` 的邊不展開，改記入 `unknown_due_to_stale` 並使 `completeness=partial` | §35.2 RESOURCE_LIMIT；不猜測 stale 邊之後的圖 |
| **D-09** | Gap：`missing_implementation`（沒有非終止 Implements 連結的 requirement）、`missing_tests`（有 Implements 但無 Verifies 的實作端點）、`stale_links`、`unverifiable`（proposed 或無 evidence）；未授權 requirement → `coverage_incomplete=true` | §35.1 GapReport 語意 |
| **D-10** | Explain：`contradicted` 優先於 `supported`；只有 validated/accepted 且帶 evidence 的連結才算數；不可讀取的 ref 計入 `omitted_due_to_access` 並使 `completeness=partial`；超出 token 預算 → `CONTEXT_BUDGET_EXCEEDED` | §35.1 EvidenceReport；不把不可見當成不存在 |
| **D-11** | `compare_revisions` 以 `record_snapshot`（seam）記錄「連結 id → (etag, state)」快照；未知快照 → `SOURCE_UNAVAILABLE` | §35.2；沒有版本庫時仍能給出 added/changed/removed，且不假裝有完整版控 |
| **D-12** | `revalidate_stale` 只在「斷言 revision == 觀測 head」時把 `stale→validated`；否則保留 `stale` 並在 job diagnostics 寫明原因；**永不自動 accepted** | §35.2「來源不可得 MUST 保留 stale」；成功路徑對應「來源回滾到斷言版本」 |
| **D-13** | Endpoint 註冊、head 觀測、快照記錄是 **seam**（`trace:admin`），不是 wire operation | 這些屬於 ingestion/policy 的輸入（P3/P4 分析結果），不應新增未經批准的 operation |
| **D-14** | `time` 模組只有 formatter（trace 只需輸出 instant）；與 `memory-domain` 的 parser 重複 | 記錄為缺口：應上移 `ukma-types`，本階段不為此改動已完成階段（避免跨階段回歸風險） |

## 5. 已知缺口（不得宣稱完成）

1. **無持久化 adapter**：links／endpoints／snapshots／jobs 全在記憶體。
2. **revalidation job 同步執行**：狀態與 diagnostics 齊備，但沒有背景 worker（同 ADR-052 缺口 1）。
3. **head 與 requirement authorisation 由呼叫端供給**：尚未接上 P3 code analysis／P4 document ingest 的實際 revision 與 ACL。
4. **`INDEX_STALE`／`INDEX_NOT_READY` 只以 `IndexFreshness` 呈現**：未實作 strict-generation 等待與 timeout。
5. **snapshot 僅記錄當下可見連結**：不是完整版本庫，rollback 不支援。
6. **跨 domain E2E 未串接**（E2E-API-03/04 屬後續階段）：目前 traceability 僅與自身 store 互動。
7. **時間工具重複**：`time::format_rfc3339` 與 `memory-domain` 的 parser/formatter 重疊（D-14）。
