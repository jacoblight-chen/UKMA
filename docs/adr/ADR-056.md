# ADR-056 生產就緒與 release evidence 實作決策（P10）

**Status: ACCEPTED**（owner 架構審批，2026-10-25）

**Spec references:** §6.2、§6.3、§17.1（REP-003、DB-002、DB-008、DB-010、OPS-001）、§28.2、§28.3、§29.4（FM-010、SR-004）、§38.3（R4、R8）
**Related:** ADR-021（無 vendor SDK）、ADR-022（能力缺口不得靜默降級）、ADR-038（fail-closed router）、ADR-048（三 profile）、ADR-055（P9 覆蓋矩陣）

## 1. Context

P10 是最後一個階段，處理「能不能交付」而不是「有沒有功能」：三 profile 的 port parity、
cutover 演練、效能基準、災難復原、授權與 release evidence。**沒有新增任何 wire operation**。

本階段的關鍵限制必須說清楚：此環境沒有 PostgreSQL / Qdrant / Neo4j，也沒有 1M episode 的
時間與硬體預算。因此 P10 的交付原則是——**能被實際執行的，就用測試固化；不能執行的，就用
機器可讀的宣告 + gate 記錄成缺口**，不以文件宣稱代替證據。

## 2. Decisions

| ID | 決策 | 理由與後果 |
|---|---|---|
| **D-01** | 三 profile parity 以**報告 + gate** 表達：`contracts/testing/port-parity.json` 宣告 A/B/C，`port_parity.rs` 對 profile A 跑**一份共用的 port contract**（metadata CAS＋revisioned read＋typed key equality、durable outbox、full text、vector profile 隔離、immutable artifacts＋reload），並要求 B/C 的 adapter 真的 `available == false` 且帶原因 | 只有 A 可執行，所以「三方等價」不成立；報告明寫 unavailable 與所需伺服器。若未來把 B 改成 available 而沒有真的通過契約，gate 會失敗 |
| **D-02** | Cutover 是 `storage-router::cutover` 的 **9 狀態機 + fencing token**：每一步只有前置條件成立才能前進（snapshot/export 需 checksum、import/verify 需筆數、shadow read 需 0 divergence），且 writer ownership 移動時 fence 遞增；`rollback` 只在 cutover 前合法 | DB-010 要的是「不會有兩個寫者」。用狀態機把「順序」與「fence」變成可測物件，而不是流程文件 |
| **D-03** | Cutover 演練的 export 必須包含**三種 canonical 資料**：metadata records、published generation manifests、**unacked outbox**（含 per-consumer ack 狀態） | 由測試抓到的真實缺陷：只搬 records 的 cutover 會讓 target 失去 generation（strict_generation 讀不到）與未投影事件。此決策把「cutover 要搬什麼」寫進程式 |
| **D-04** | 效能基準用**新的 `ukma-bench` crate**，透過 public API 跑確定性工作負載，輸出 JSON（command/profile/hardware/workload/results/not_measured）並把報告 commit 進 repo | FM-010 要求「可重現配置與報告」。報告含 `not_measured`（RSS/VRAM、第二後端、1M 規模），避免把未量測項目當成已量測 |
| **D-05** | 基準同時提供 **2k 基準線**與 **20k 規模探測**；20k 的 `RESOURCE_LIMIT`（`MAX_CANDIDATES=10_000`）記錄為**有界正確行為**與規模限制，不視為通過 | 讓讀者看到「寫入與規模無關、詞彙檢索 O(n) 且受候選上限約束」，因此 FM-010 維持 partial（1M 需 ANN/分區） |
| **D-06** | 災難復原演練是真檔案操作：backup＝複製 store 檔＋artifact 位元組；disaster＝刪除或截斷 live 檔；restore＝回拷；re-index＝從 canonical＋outbox 重建 derived；rollback＝留在 `retained` generation | OPS-001 要求 backup/restore、re-index、rollback 演練。全部可在 embedded+filesystem 上真跑，因此 **OPS-001 由 gap 轉為 covered** |
| **D-07** | 授權審計以 `cargo metadata --locked` 產生的 `contracts/testing/third-party-inventory.json` 為機器可讀來源；`release_evidence.rs` **重新推導**每個決定（允許清單、`OR`/`AND`/舊式斜線 disjunction、GPL/AGPL/SSPL/BUSL/Elastic/Commons-Clause 家族）並與檔案比對，且與 `Cargo.lock` 完全對齊 | 「記錄」與「判斷」分離：檔案記錄決定，測試重算決定。新增依賴未更新清單 → build 失敗；引入 copyleft-only 依賴 → 永遠失敗。**REP-003 由 gap 轉為 covered** |
| **D-08** | 根目錄補上 `LICENSE`（Apache-2.0 全文）與 `NOTICE`（UKMA 版權＋CodeGraph/Andrey Vasilevsky 歸屬＋pinned commit＋指向 inventory） | REP-003 要求 LICENSE/NOTICE/第三方審計。NOTICE 的歸屬文字與 `docs/migration/upstream-lock.yaml` 一致，並由測試驗證兩者相符 |
| **D-09** | Release evidence pack 由測試列舉並驗證存在且非空（LICENSE、NOTICE、覆蓋矩陣、port parity、inventory、license audit、upstream lock、implementation status、效能基準、ADR-055/056） | R8 要的是「reviewer 可以打開的東西」，不是一句「已完成」 |
| **D-10** | Pipeline 維持 Rust-only；bench 與 integration 皆為 `publish = false`，不引入 async runtime、資料庫 SDK 或 HTTP framework | 與 ADR-021 一致；`arc001`/`db001` 仍會擋住任何 backend SDK 進入 workspace |

## 5. 已知缺口（不得宣稱完成）

> **部分項目已由 ADR-057 收尾**：第 1 項的 profile B 已實作為真正的 SQL（SQLite）後端、
> 第 2 項的 1M episode 已達標、第 3 項 RSS/on-disk 已量測、第 4 項已補 backup 排程與 SBOM。
> 仍然有效的是：profile C（需三台伺服器）、SBOM 未簽章、JSON Schema 仍 preliminary。

1. **Profile B / C 未實作**：postgres/qdrant/neo4j/sqlite adapter 仍宣告 unavailable，因此「三方等價」與 `SR-004` 不成立。
2. **1M episode 未達標**：詞彙檢索 O(n) 且受 10 000 候選上限；需要 ANN（HNSW）或分區查詢。
3. **RSS / VRAM / on-disk 索引大小未量測**：報告中為 `null` 並附原因。
4. **無 backup 排程與保留政策**：DR 演練是手動流程的程式化版本，沒有 scheduler。
5. **無 release 簽章／SBOM 產生器**：evidence pack 是檔案清單，不是簽章成品。
6. **JSON Schema 仍為 preliminary**：manifest 覆蓋 ≠ schema closure（§31.3.1），本階段未改變此狀態。
