# ADR-059 — Canonical schema migration and SBOM signing

- Status: accepted
- Date: 2026-10-25
- Closes: FM-006 (canonical schema versioning/migration) from ADR-057's gap list, and the
  "no signing capability" limitation recorded in ADR-056/057
- Related: ADR-057 (remaining gaps), ADR-058 (schema closure)

## 1. Context

Two items were reported as unfinished after P10:

1. **FM-006** — the embedded snapshot carried a `format` number and refused unknown values, but
   no migration existed. A canonical store can therefore never change shape, and a store written
   by a newer build could not be reasoned about at all.
2. **SBOM signing** — the digest manifest recorded `signature: null` and the note said a signature
   needs a key the build does not hold. That was honest, but it meant no signing mechanism existed.

## 2. Decision — canonical schema migration (FM-006)

- `storage_ports::migration` owns the contract, with no database dependency:
  - `SchemaVersionPort` — read/write the persisted canonical schema version;
  - `Migration` — one forward-only step with `version`, `name`, `apply(&dyn MetadataPort, &ScopeRef)`;
  - `migrate()` — the runner, plus `MigrationReport { from, to, applied, skipped }`.
- The runner is fail-closed:
  - a store **newer** than the requested target is refused with `INVALID_SCHEMA`
    (`SchemaVersionUnsupported`) instead of being opened or downgraded;
  - the chain must be **contiguous** from the stored version to the target
    (`MigrationChainBroken`), so a missing step cannot be skipped;
  - the version is advanced **after** a step succeeds, so a crashed run resumes at the failed
    step rather than replaying a half-applied one;
  - re-running against an up-to-date store is a no-op (`skipped: true`).
- Two real steps ship in `storage_ports::migrations`:
  - **v1 `baseline`** — reaches v1; a fresh store already satisfies it;
  - **v2 `stamp-schema-version`** — pages every canonical record with the store's own cursor and
    CAS-writes `schema_version: 2` into it, so a concurrent update conflicts instead of being
    overwritten.
- Where the version lives:
  - `EmbeddedStore` persists `schema_version` in the snapshot; snapshots written before this ADR
    load as **v1** (`#[serde(default = "legacy_schema_version")]`), a brand new snapshot starts at
    `CANONICAL_SCHEMA_VERSION`;
  - `SqliteStore` stores it in a `canonical_schema` table created on demand. This is deliberately
    *separate* from `PRAGMA user_version`, which stays the adapter's physical DDL version — one is
    the logical contract, the other is a file layout, and conflating them would make an adapter
    upgrade look like a data migration.

Evidence: 6 unit tests in `crates/storage-ports/src/migration.rs` (order, idempotence, newer-store
refusal, broken chain, target beyond the chain, failing step) and 7 contract tests in
`crates/ukma-integration/tests/schema_migration.rs` that run **the same** cases against both
adapters, including "the version survives reopen" and "a foreign scope is not rewritten".

## 3. Decision — SBOM signing

- New tool crate `tools/release-evidence` (`ukma-release-evidence`), the single Rust implementation
  of the derived release evidence (it replaces the ad-hoc scripts used for ADR-057/058):
  - `regenerate` — rewrites `third-party-inventory.json`, `sbom.cyclonedx.json` and
    `sbom.digest.json` from `cargo metadata --locked`;
  - `check` — re-derives all three and fails on any drift;
  - `generate-key --out <file>` — writes a 32-byte Ed25519 seed using the OS CSPRNG;
  - `sign --key <file> [--out <file>]` — signs the SBOM **digest** and writes
    `contracts/testing/sbom.signature.json` with `algorithm`, `signed_file`, `sha256`,
    `public_key`, `signature`;
  - `verify [--sig <file>]` — recomputes the digest, checks it against the signature record, and
    verifies the Ed25519 signature with the recorded public key.
- The **private key never enters the repository**. `docs/migration/license-audit.md` documents the
  release procedure; the committed digest keeps `signature: null` until a release key exists.
- A new gate (`a_present_sbom_signature_must_match_the_current_sbom`) refuses a committed
  signature that covers an older SBOM, so a stale signature cannot masquerade as provenance.

Evidence (executed on 2026-10-25): `generate-key` → `sign` → `verify` round-trips on a throwaway key
outside the repository; the tool's 6 unit tests cover the licence policy, determinism, the
sign/verify round trip, tamper detection, key mismatch and malformed keys.

## 4. Consequences

- Coverage: `FM-006` moves from **gap** to **covered**; the matrix is now
  **covered 64 / partial 5 / gap 0** of 69 classified ids.
- Dependencies: the tool adds `ed25519-dalek`, `curve25519-dalek`, `signature`, `zeroize`,
  `rand_core`, `getrandom`, `cpufeatures` (all permissive). The inventory/SBOM were regenerated by
  the new tool: **351 components (321 external, 30 workspace), 0 unlicensed, 0 blocked**.
- Also fixed on the way: `code-intelligence` referenced the optional `tree-sitter` substrate
  unconditionally, so the crate only built when at least one grammar feature was enabled. The
  substrate is now a hard dependency (grammars stay optional) and the parser-dependent test files
  are gated, so every feature combination builds:
  `--no-default-features`, `--no-default-features --features parser-rust`,
  `--no-default-features --features parser-s2-batch2` and `--all-features` were all checked.
- Validation (executed): `cargo fmt --all -- --check`, `cargo check --workspace --all-targets`,
  `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace --all-targets`
  (**703 passed, 0 failed**), `cargo run -p ukma-contract-check` (**5411 checks, 0 failed**),
  `cargo run -p ukma-release-evidence -- check`.

## 5. What this does not claim

- Profile C parity (PostgreSQL + Qdrant + Neo4j) is still unavailable: this machine has no Docker,
  no `psql` and no service endpoints, so those adapters stay `declared-unavailable` and the
  three-way equivalence in `contracts/testing/port-parity.json` remains **not verified**.
- The SBOM in the repository is **not signed**; what is proven is that signing and verification
  work and are gated. A release must supply a key.
- `claim_level.implementation_compliant` and `production_ready` stay **false**.
